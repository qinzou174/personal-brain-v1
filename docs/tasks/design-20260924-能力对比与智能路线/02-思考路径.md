### 0.2 每个接缝的运行原理（一句话，生产→处理→消费）

- **工具面**：客户端经 MCP 调 `tools/call` → `AuthorizedToolService` 先 `authenticate` 再 `authorize` → 命中领域操作 → 返回结构化结果；**入口处无模型参与**。
- **检索**：查询文本 + 可选 embedding → `SearchRepository.search` 先按 owner/scope/sensitivity/valid_to 硬过滤 → FTS 与 pgvector 各取 50 → RRF(k=60) 融合 → 取前 N 返回带 source_links 的 hit。
- **接地问答**：query → 权限过滤检索取证据 → 若空则直接返回"没有找到足够的已授权知识"（`grounded=False`）→ 否则带证据调一次模型 → 返回 answer + sources。
- **通知**：事件 → `evaluate_trigger` 判定是否通知 → 通知策略做合并/冷却去重 → worker 投递到 owner Inbox。
- **后台作业**：DurableJobPoller 取租约 → 按 job_type 分派 → 幂等提交或重试/死信；**全部是"被触发"型，无时间驱动**。

**白话总结（讲给不读代码的人）**：你的 Brain 是一间**有严格档案管理的图书馆**。有人来问，它按你的权限去查，查不到就老实说查不到，绝不许馆员瞎编；它把每本书的来源、版本、能不能看都记得清清楚楚。但它**不会自己出门办事，也不会主动给你打电话**。

## 一、我理解的项目哲学内核（用自己的话，不抄条文）

### 1.1 一句话：这个项目在造什么

> **它在造一份"你说过的话，永远算数"的个人权威记忆——任何 AI 模型、任何账号、任何客户端都可以换掉，但这份记忆不换，而且每一条都能追溯到原始证据。**

不是"AI 陪伴系统"，不是"个人知识库"，不是"RAG 应用"。它交付的产品是**可信上下文**，不是对话体验。

### 1.2 四条不可让渡公理（附"工程上最易踩塌的形态"）

| # | 公理 | 工程上最易踩塌的形态 |
|---|---|---|
| A1 | **权威单一且服务端**（FR-001/FR-002）：客户端可替换，记忆不可分散 | 为了让某个客户端好用，把状态缓存到客户端本地，久而久之客户端变成第二权威 |
| A2 | **原始先于派生**（FR-004/FR-005/ER-01）：派生永不改写原文，且必须带证据、生成版本、生命周期 | 新模型"更好地"重写摘要时直接覆盖旧摘要，历史解释权被抹掉 |
| A3 | **权限先于检索**（FR-067/ER-06）：授权失败发生在搜索之前，不是搜完再过滤 | 为了"召回率"先全量搜再删结果，敏感内容已进入进程内存/日志 |
| A4 | **诚实优先于成功**（FR-084/FR-087/ER-07）：不确定必须报不确定，不得假称完成 | 离线时回执写 `completed` 而不是 `pending_sync`，用户以为存住了 |

### 1.3 一个辨析例（证明我读懂了，而不是引用了编号）

**现象**：`answer_brain` 在检索为空时返回固定话术"没有找到足够的已授权知识来回答"，且 `grounded=False`（`authorized_tools.py:260-264`）`[已验证]`。

**直觉判断**："这是功能缺失——它不会聊天。"

**正确判断**：**这是 A4 的忠实执行，哲学上是对的。** 若让模型在无证据时自由发挥，就等于允许"派生内容在没有 canonical 来源的情况下进入答案"，直接违反 A2 + ER-01（派生必须带 source IDs）。这不是 bug。

**这个辨析改变了什么修法方向**：
- 错误方向 = "给 Brain 加自由聊天能力"（等于亲手拆掉 A2/A4，把项目退化成 AnythingLLM）。
- 正确方向 = **"加一个独立的动作面，让它仍然不许瞎编"**——答案仍须有证据；但"做事"可以没有"知识证据"，因为它有**执行证据**（operation 记录、回执、可回滚日志）。

**这就是本次反思的方向性结论：智能不是"让它更会说话"，是"让它有一双手，并且这双手带档案"。**

## 三、分层根因（为什么"智能"接不上）

> 注意：这里**不存在"现有机制被架空"**的情形。现有机制没有被架空，它们工作得很好——**问题是契约层从根上不表达"动作"，所以任何智能都只能是外挂**。这比"机制被架空"更根本。

### L1 目标层（哲学错位）
- **白话**：不是做不到，是**当初就有意不做**。V1 把"高容量主动消息、自主多智能体社会"写进了 Out of Scope（spec.md:49-52）。
- **证据**：`spec.md:49-52` `[已验证]`
- **独立修法**：**改需求文档，不改代码**。若决定要智能，先在 spec 里把这条 Out of Scope 降级为"V1.1 候选"，并在 ER 里给新的主动性边界。

### L2 契约层（功能缺失的根源）
- **白话**：30 个工具是"笔记本"，不是"手"。契约层没有动作动词，任何循环都无处落脚，只能在客户端外挂；而客户端外挂拿不到 Brain 的权威状态。
- **证据**：`protocols/tools.py:32-40` `[已验证]`
- **独立修法**：在工具面新增"动作型工具命名空间"，先只读（读取/检索/计算），每个动作强制带 `operation_id`。

### L3 运行时层
- **白话**：worker 只会在被叫到时干活（7 类被触发作业），没有"到点自己醒"的能力。
- **证据**：`job_handlers.py` 作业类型；`us11-proactivity.md:19-20` 调度器未接线 `[已验证]`
- **独立修法**：给 worker 增加调度源（cron/interval），但**调度只负责"唤醒"，不负责"决定做什么"**——决定权仍在策略层，以保住 FR-090。

### L4 通道层
- **白话**：只有 Inbox 一个出口，且 Inbox 只在客户端打开时才被看到。
- **证据**：grep `smtp/telegram/webhook` 零命中；`us11-proactivity.md:18` 明确渠道未实现 `[已验证]`
- **独立修法**：分阶段——先增强 Inbox，再引入**单一"发给自己"**通道；"可发给他人"必须留在 V2。

### L5 模型层（关键摩擦点）
- **白话**：ER-12 的"每任务最多 2 次模型请求 + fail-closed 预算"是**质量资产**，但它和 agent 循环（几十次调用）天然冲突。
- **证据**：`models/gateway.py:70-109`；`execution-rules.md:112` `[已验证]`
- **独立修法**：**不动全局预算**，为循环开独立预算域；循环域超限时降级为"只读总结"，而不是静默扩权。

## 四、参照系（该学 / 不该学 / 本项目独有约束）

### 4.1 AnythingLLM
- **它是什么**：本地优先的文档 RAG + Agent 工作台，MIT，66k+ stars，含 Model Router、Scheduled Jobs、自动记忆、MCP、多租户 `[已验证]`。
- **对得上本项目什么**：它的 **Scheduled Jobs + 推送通知**（v1.13.0）正是本项目缺的"闹钟"；它的 **工作区记忆（workspace/global memory bank）** 是本项目 `self_claims` 的粗粒度简化版 `[已验证]`。
- **该学**：定时任务的**产品化程度**（可视化 cron、运行历史、推送点击直达）；"零配置可用"的入口体验。
- **不该学**：把记忆当 chunk 的取巧——它无法回答"我为什么相信这条"，而这正是本项目全部价值所在。
- **独有约束**：本项目的记忆带证据血缘与权限交集（ER-01），**不能被摘要洗掉权限**；因此不能照搬它的"记忆库"抽象。

### 4.2 OpenClaw
- **它是什么**：MIT 开源个人行动体，25–29 个聊天通道，记忆落地为本地 Markdown（`MEMORY.md` + 每日笔记 + 语义召回），有 cron/heartbeat/webhook 主动触发，能读写文件、跑命令、控浏览器 `[已验证]`（架构细节来自第三方综述 `[推断]`）。
- **对得上本项目什么**：它的 **Gateway → Runtime → Tool Loop** 三层，正是本项目缺的那三层；它的"一条消息触发几十次工具调用"是"智能"的直观刻度。
- **该学**：**循环的形态**（工具结果回灌上下文再决策）与**通道优先**的产品直觉。
- **不该学**：**记忆用明文 Markdown、无证据血缘、无幂等墓碑**——它的记忆可被人手改，也可以被模型重写；本项目 A2 明令禁止。
- **独有约束**：本项目是**单用户单权威域**（FR-001），而 OpenClaw 面向"分享给团队"；它的多租户思路与本项目的 scope 交集模型不同源，不能混用。

### 4.3 Hermes Agent（Nous Research）
- **它是什么**：MIT，2026-02 发布，持久记忆 + **自动生成技能**（SKILL.md 开放标准）+ 多平台网关 + cron 调度 + 并行子智能体 + 五种沙箱后端 `[已验证]`。
- **对得上本项目什么**：它的**自动技能生成**对应本项目"动作模板可复用"的缺口；它的**并行子智能体**对应"一个请求可拆多路只读检索"。
- **该学**：**把"做过的事"沉淀为可复用资产**——这与本项目 ER-01（派生必须可追溯）天然相容，是本项目最容易吸收的一条。
- **不该学**：**无边界自主执行**（默认全系统访问 + 沙箱）。本项目 ER-06 要求高风险动作强制确认，且"模型文本里的'用户已确认'不是凭证"（`execution-rules.md:68`）。
- **独有约束**：本项目的动作必须落 canonical 事件并进删除账本（ER-01/ER-09），而它的动作只留轨迹；因此不能照搬"技能即代码"的自由度。

### 4.4 本项目独有约束（所有参照都没有、不能硬套）

1. **单用户单权威域**（FR-001/FR-002）：没有"多实例物理隔离"、没有"双端权威 A/B"——这是本项目的形态，不是参照系的形态。
2. **证据血缘不可绕过**（ER-01）：派生 scope = 来源权限交集，敏感级别不低于最敏感来源；删掉最后一个来源则派生转 `orphaned`。
3. **幂等与断网四态**（ER-07）：`canonical_committed / durable queued / local only / OUTCOME_UNKNOWN`——动作面必须复用同一套。
4. **确认门是唯一凭证来源**（ER-06）：确认记录须来自 owner 审阅通道，含 `operation/target IDs/payload_digest/expected_version/risk/expires_at`，15 分钟有效、单次消费。
5. **删除账本先于服务**（ER-09）：恢复后对外服务前必须重放删除账本——动作产生的新事实也必须进账本。

### 8.2 对话层白话总结

**一句话**：你的项目不是"不够聪明"，是"没有手和闹钟"；而它已经有了一双**带档案的手**所需要的全部前提——所以它离"智能"比看起来近得多。

**关键发现（6 条）**：
1. 30 个工具全是"笔记本"动词，没有一个是"手"（`tools.py:32-40`）。
2. `answer_brain` 被硬限 1 次模型调用——这是架构天花板，不是模型天花板。
3. 全仓零通道代码，效率的瓶颈是**触达**，不是能力。
4. ER-03 规定的排序决胜项与 `ranking_reasons` **代码里零实现**——一条"规范写了、没接线"的悬空条款。
5. "不智能"是 **spec 里写明的有意决策**（spec.md:49-52），不是疏漏；要改就得改需求。
6. ER-12 的"每任务最多 2 次模型请求"与 agent 循环**结构性冲突**，必须先划边界再动手。
