> 对象：Personal Brain V1 后端"活起来"——为何没有越变越聪明、LLM/向量模型未充分利用。
> 证据分层：`已验证`（文件:行号/实测）｜`推断`｜`未知`。
> 宪法来源：`工程母提示词.md`（全文已读，本会话）。

## 一、我理解的项目哲学内核（用自己的话）

**一句话**：这个项目在造"一个不随软件/账号/模型更换而消失的个人数字记忆基础设施"——数据属于用户，AI 只是它的不同客户端；原始事实永久保留，AI 派生必须可追溯、可重建、可被证据回溯。

**不可让渡公理**（我的提炼）：
1. **原始事实 > AI 摘要**（§2.3）：raw 永不因已总结而删除；派生可重建。
2. **结构化优先于概率化**（§2.5/§58）：金额/待办走 SQL；只有"想法/语义"类才交给检索。
3. **推断不冒充事实**（§2.6/§9）：AI 推断必须带 confidence/source/evidence；A/B/C 分级。
4. **增量演化而非覆盖**（§7/§82-83）：偏好从 candidate 随证据升级，变化保留历史不抹除。

**辨析例（证明理解）**：我问"我买了咖啡吗"——系统答"无法确认"而**不是**编一个。这符合公理 3：证据不足时诚实弃权比"看起来智能"更重要。同理，记账走固定规则而非 LLM 猜测（§16），这是**故意设死**的正确设计——真正的缺陷在别处：**该活的层没有通电**。

## 三、分层根因（为什么"活不起来"）

**第 1 层：作业排产与处理器能力脱节**（白话：工具间没连上）
- `extract_raw_input` 排了作业，但没有对应的 LLM 抽取 handler——被复用成 index。修法：新增独立 `extract` handler（LLM 抽取→候选派生），与 index 分离。`[已验证]`

**第 2 层：域逻辑与运行时无桥**
- `assess_b_promotion`/`plan_retention`/`lifecycle` 是"纯域"，但**没有任何作业/触发器调用它们**。修法：新增 `promote_candidates`/`retention_sweep` 作业 + 定时排产。`[已验证]`

**第 3 层：调度器缺失**
- 现有作业全部是"事件驱动"（用户调用排一个），**没有周期性调度**（无 scheduler/cron）。Digest、升级、retention、冲突检测都依赖"定期跑"。这是"活"最底层的缺口。`[已验证]`

**第 4 层：为什么被架空——测试假设代替了运行时验证**
- 单测直接调 `assess_b_promotion`（`test_memory_policy.py:34`）证明"逻辑正确"，但**没有一条端到端测试验证"用户连续记录 3 次同类偏好后，画像自动升级"**——测试覆盖了函数，没覆盖"它是活的"。这解释了为什么 450+ 测试全绿却"死"。`[推断，依据：测试文件清点]`

**第 5 层：LLM 预算纪律反向成为惰性**
- `ModelGateway` 每次调用有预算/超时约束（`gateway.py`），设计正确；但没有"批量/后台批处理"通道，导致**没人敢在后台主动调 LLM**。修法：后台派生作业使用独立的、更宽的预算策略（仍 fail-closed）。`[推断]`

## 四、参照系（该学/不该学）

| 参照 | 是什么 | 对得上本项目什么 | 该学 / 不该学 |
|---|---|---|---|
| **Generative Agents**（Park et al. 2023 记忆流） | 记忆=带时间戳的观察流+重要性评分+反思层（定期生成高层洞察） | 对应 §82 升级、§78 Digest、§12 冲突 | **学**：反思作业（定期把零散 observation 总结为高层 insight）；**不该学**：其"重要度由 LLM 打分驱动所有召回"——本项目要求确定性优先（§96），重要性只能作为排序信号之一 |
| **CoALA**（认知架构） | 记忆分工作/情景/语义/程序四类 + 内部行动（推理/检索/学习）循环 | 对应 Intake→派生→升级闭环 | **学**："学习"是显式动作（把 episodic 提炼为 semantic）；**不该学**：完整四层分类过度工程化，本项目已用 canonical/derived 二分 |
| **MemGPT**（虚拟上下文管理） | 分层记忆+自主编辑记忆 | 对应 Digest/压缩 | **学**：自主维护（归档/摘要）作为后台作业；**不该学**：让 LLM 自主改写核心记忆——违反本项目"AI 不得随意修改 Self Model"（§4） |
| **RAG 反思循环**（Self-RAG/CRAG） | 检索→评估→再检索 | 对应检索质量 | **不该学（V1）**：引入检索时 LLM 评估会增加延迟与不可控性；本项目排序必须可解释（ER-03） |

**本项目独有约束（不能硬套任何参考）**：
1. 单用户、本地优先、长期运行（不是多租户云服务）；
2. **确定性优先**（§96）：能代码做的不用 LLM；LLM 只用于"理解/提炼"不可规则化的部分；
3. 事实分层（canonical/derived/A-B-C）是硬约束——所有"活"的动作必须分类型、带证据、可回溯；
4. 失败必须诚实（断网/无线索时明确说"没有"，不假装）。

## 五、思维链（因为 X → 所以 Y → 预期 Z）

1. 因为 §14 要求 Raw Input 派生结构化内容 → 所以 `extract_raw_input` 必须有真正的 LLM 抽取 handler → 预期：记一条含地点的日记后，库中出现派生的 candidate 记录（可查询验证）。
2. 因为 §82 要求候选随证据升级 → 所以 `assess_b_promotion` 必须被周期性作业调用 → 预期：同类偏好记录 3 次后 lifecycle_state 从 candidate 变 established（机检）。
3. 因为 §83/§11 要求保留策略按类型执行 → 所以 `plan_retention` 必须接入定期扫描 → 预期：超过 90 天无新证据的 candidate 自动归档（机检）。
4. 因为"活"依赖周期性而非仅事件驱动 → 所以必须有**调度器**（cron 式作业排产）→ 预期：每天自动出现 digest/升级/retention 作业记录（jobs 表可查）。
5. 因为 §94 要求派生带版本、可重建 → 所以 `provider_derive` 必须被真实排队（至少 digest/抽取产生派生内容时）→ 预期：`derived_contents` 出现生产数据（当前为零）。
6. 因为 §96 要求确定性优先 → 所以调度与升级判定**不调用 LLM**（纯 SQL+域函数），只有"抽取/摘要"才调 LLM → 预期：每日 LLM 调用量可控（个位数~几十次），成本可预测。
7. 因为 §12 要求冲突进 Inbox 而非静默 → 所以新证据与 established 画像矛盾时自动生成 review item → 预期：产生矛盾的记录后 `review_inbox_items` 出现新项（机检）。
8. 因为 §78 Digest 是"导航层" → 所以 digest 必须引用 raw 而非替代（链接 source_links）→ 预期：digest 内容可回溯到原始条目（source 完整率 100%）。
9. 因为 §74 要求主动克制 → 所以 V1 主动项只做 health/job 失败/备份检查 → 预期：无用户交互日，系统仍产出 health 状态（可观察）。
10. 因为第 4 层根因（测试假设代替运行时）→ 所以每条"活化"改动必须配**端到端行为测试**（"连续记录→自动升级"）→ 预期：新的测试能失败于旧代码、通过于新代码。
11. 因为 LLM 后台调用有成本风险 → 所以必须沿用 ModelGateway 的预算/超时/敏感度约束并加每日配额 → 预期：超额时降级为"仅规则"，不阻断写入。
12. 因为用户要"越用越懂我" → 所以核心验证不是功能存在，而是**跨天行为**：第 1 天记录、第 3 天问"你了解我什么"能得到带证据的升级画像 → 预期：一周试用后 answer_brain 的画像类回答出现 established 条目。

## 六、表现指标（三线 + 反退化红线）

| 线 | 指标 | 机检口径 | 现状值 | 目标值 |
|---|---|---|---|---|
| 最低线 | 抽取派生通道通电 | `derived_contents` 生产行数 > 0 | 0 | >0（每次含可抽取内容的记录产生派生） |
| 最低线 | 调度器在跑 | `jobs` 表周期性作业类型 ≥2 种出现 | 0 种 | digest + promotion 每日出现 |
| 中间线 | 画像自演化 | candidate→established 的自动转换记录数 | 0 | 试用一周内 ≥3 条自动升级 |
| 中间线 | 冲突自动进 Inbox | 矛盾记录产生 review item | 0 | ≥1（构造矛盾测试） |
| 高线 | 跨天"懂我" | answer_brain("你了解我什么") 回答中 established 条目占比 | 0% | >50%（一周真实使用后） |

**反退化红线**（违反即失败）：
1. **不许**让 LLM 参与金额/待办判定（§16/§96 结构化优先）；
2. **不许**让后台 LLM 派生结果直接成为 canonical 事实（必须 derived + confidence，§2.6）；
3. **不许**静默覆盖画像（升级/降级/冲突必须留痕可回溯，§7/§12）；
4. **不许**在无证据时编造（digest/回答必须可回溯 source，§9）。

## 七、设计 Delta（优化方案）

> 分四期，按依赖排序；每期可独立验收。全部沿用现有表结构（无需迁移，`derived_contents`/`self_claims`/`review_inbox_items`/`jobs` 已齐备）。

### Δ1 调度器（"活"的地基）— 最高优先级
- **改什么**：新增 `scheduler` 组件（worker 内轻量 cron：一个 `schedule` 表或代码内 cron 定义），每日/每小时排产周期性作业（digest/promotion/retention/conflict-scan）。
- **依据**：第 3 层根因；§80 Maintenance"不能只会写入"。
- **预期**：jobs 表出现周期性作业记录；无用户交互也运行。
- **工程量**：小（1 个组件 + 1 张表 + 排产逻辑）。

### Δ2 抽取派生接通（LLM 用起来·第一批）
- **改什么**：把 `extract_raw_input` 从 index handler 拆出：新 `extract` handler → 调 LLM（ModelGateway，受预算约束）→ 从 raw 文本抽取候选（地点/经历/偏好候选/事件）→ 写入 `derived_contents` + 生成 candidate（进 self_claims 或 events）→ 派生内容带 source 链接。
- **依据**：§14 派生；差距 #1/#4；思维链 1/5/6。
- **预期**：记日记后出现派生候选；`derived_contents` 生产行数 >0。
- **工程量**：中（handler + 抽取 prompt + 落库 + 测试）。

### Δ3 画像自演化接线（LLM/域逻辑用起来·第二批）
- **改什么**：新增 `promote_candidates` 作业（调 `assess_b_promotion` + `lifecycle`）+ `retention_sweep`（调 `plan_retention`）+ `conflict_scan`（新证据×established 画像矛盾 → review item）。
- **依据**：§82/§83/§12；差距 #2/#3/#6；思维链 2/3/7。
- **预期**：同类偏好 3 次后自动升级；无证据 90 天归档；矛盾进 Inbox。
- **工程量**：中（3 个 handler，域逻辑已有，主要是接线 + 端到端测试）。

### Δ4 主动智能（Digest + 克制的主动）
- **改什么**：`daily_digest` 作业（当日 raw → LLM 摘要 → 导航层，带 source_links）+ health 类主动检查（job 失败/备份过期 → notifications）。
- **依据**：§78/§74；差距 #5/#8；思维链 8/9。
- **预期**：每日 digest 可查；health 异常有通知记录。
- **工程量**：中（2 个 handler + 摘要 prompt）。

### 决策点（交创始人拍板）

| 决策 | 选项 | 建议 |
|---|---|---|
| D1 LLM 后台预算 | (a) 沿用单次 max_calls=1 严纪律 (b) 为后台批量派生设独立宽预算（如每日 200 次上限） | **(b)**：否则"活"会被预算卡死；用日配额而非单次限制管控成本 |
| D2 抽取的落地目标 | (a) 只进 `derived_contents` 展示 (b) 自动生成 self_claims candidate（B 类） | **(b)**：这才产生"越用越懂"；A/C 类仍走原规则不自动 |
| D3 Digest 频率 | (a) 每日 (b) 每周 | **(a)**：V1 数据量小，日度反馈快，便于试用期验证 |
| D4 冲突检测强度 | (a) 仅记录进 Inbox (b) 同时降 confidence | **(a)**：V1 保守，人工确认后再动（符合 §12 just-in-time） |
