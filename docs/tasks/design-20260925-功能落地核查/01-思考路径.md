# 功能落地核查：故事承诺 vs 代码/运行真相（deep-reflection）

> 对象：本会话连续讲述的"档案馆"系列对知识库行为的承诺（分类/索引/变更/防串味）。
> 触发：用户追问"目前本知识库程序能够实现这些逻辑和功能吗？"
> 方法：deep-reflection 九步（可裁剪）；证据分层 `已验证`｜`推断`｜`未知`。
> 证据来源：本会话代码核验（文件:行号）、生产库只读查询（192.168.10.7:18083，11:5xZ）、
> 本机实例 18:03–18:04 的实跑记录（该实例 18:41 被正常停机，pid 文件已清理，疑为用户/并行会话主动停）。

## 一、我理解的项目哲学内核（用自己的话）

**一句话**：造一个不随软件/账号/模型更换而消失的个人数字记忆基础设施——原文永久、派生可重建、
推断不冒充事实。

**不可让渡公理（提炼）**：① 原始记录 > AI 摘要（raw 只增不改）；② 结构化优先（金额/待办走 SQL，
不靠语义猜测）；③ 推断必须带证据与 confidence，且不得直接成为事实；④ 变化是"增量演化"，
历史永不抹除。

**辨析例**：一条含疑似密码的笔记被保密门禁拦下、没有外发给模型——它**不是 bug**（违反"不外发"
才是 bug）；真正的缺陷在别处：**写入口没拦、外发口才拦**，导致"半条命"记录（在库、搜不到）。
这个辨析直接决定修法方向（补写入口提示 or 本地降级），而不是把保密门禁拆掉。

## 四、分层根因（为什么会出现"故事漂亮、现实打折"）

1. **第 1 层（测试假设代替真实流量）**：测试用"构造时间/构造冲突"验证机制，真实系统里这两样都要等
   或要用户恰好写出对应话术。修法：把"待真实触发"的通道登记成观察项（下表指标），而不是当成已验收。
2. **第 2 层（门禁位置不一致）**：同一套保密检测在"资产上传"路径做了写入前拦截，在"笔记写入"路径
   没做，于是内容先入库、再被外发口拒绝 → 半条命。修法：让写入口与上传口同源（要么都拦、要么都降级）。
3. **第 3 层（运维路径缺失）**：重建/回填类能力只存在于代码注册表，没有"谁来点"的入口。修法：给出
   CLI/作业入口或明确登记为"保留能力"。
4. **第 4 层（叙述层与证据层脱钩）**：故事为了易懂使用了"灰尘/夜班/照片"等比喻，把"已实现但未实战"
   说成了"已经在做"。修法：叙述层显式带证据等级（本文件即纠正）。

## 五、参照系（各留边界）

| 参照 | 是什么 | 对得上本项目什么 | 该学 / 不该学 |
|---|---|---|---|
| gitleaks / GitHub secret scanning | 代码托管侧的凭据扫描，命中即拒绝入库 | "写入口就该拦" | **学**：门禁放在入口、错误信息可解释；**不该学**：它们拒绝即丢弃，本项目要求原文永存（只能"拦外发、留本地"或"拒收并告知"） |
| 全文引擎的 partial indexing | 部分字段失败仍保留其他索引 | "半条命"记录的修法 | **学**：本地关键词卡片可先建、语义通道可缺省并标 warning；**不该学**：静默降级——本项目必须把降级写进卡片 warning 与作业结果 |
| 双时态数据库（valid_from/valid_to） | 事实带生效/失效区间 | 偏好变更的"到期"建模 | **学**：变更=旧记录写 valid_to + 新记录写 valid_from；**不该学**：自动改写历史行（本项目要求只增不改，只能追加"失效标记"） |

**本项目独有约束**：单用户本地优先；既不能外发凭据、又不能丢失原文；一切降级必须可解释（排序理由/作业
结果/通知三处可见）。

## 六、思维链（因为 X → 所以 Y → 预期 Z）

1. 因为生产真实流量已跑通索引/抽取（7 条笔记）→ 所以"核心链路有效"可以宣告 → 预期 Z：卡片数、
   派生数、候选数随写入线性增长（机检：`search_index_entries` 与 `derived_contents` 计数）。
2. 因为保密门禁只在两处外发口生效 → 所以"含疑似凭据的笔记"必然半条命 → 预期 Z：每次此类写入产生
   2 条 `SECRET_REJECTED` 死信（当前事实如此）。
3. 因为写入口与资产上传口门禁不一致 → 所以修法只能是"补齐写入口策略"而不是拆门禁 → 预期 Z：同类
   笔记不再产生死信，且不被外发。
4. 因为冲突/升级需要真实样本与真实时间 → 所以本报告不能把它们算作"已验收" → 预期 Z：观察项指标
   在 1–2 周内出现非零值（或明确记录"未出现"）。
5. 因为重建/回填无运维入口 → 所以"可重建"目前只是性质、不是能力 → 预期 Z：给出入口后能实测一次
   全量重建（卡片数守恒）。
6. 因为叙述层未带证据等级 → 所以用户会把"已实现"理解成"已验证" → 预期 Z：后续故事/报告统一带
   ✅已跑通 / ⚠️有测试未实战 / ⛔未实现 三档标记。
7. 因为健康检查把死信计入通知 → 所以这次的真实故障会在下次巡检再次提醒 → 预期 Z：通知数与死信数
   同向变化（当前 4 条死信）。
8. 因为原文只增不改 → 所以即使"半条命"修好，也只需补跑该条的处理，不需要重写历史 → 预期 Z：修复
   后该 raw 的卡片与派生补齐（幂等重放）。

## 八、设计 delta（从链条引用，候选）

- **Δ1（建议立即）**：统一保密门禁位置——`save_note` 写入前做同源 `detect_secret`；
  命中时二选一（决策点 D-A）：
  - (a) 拒收并明确告知客户端（与资产上传一致）；
  - (b) 收下原文、**只建本地关键词卡片、跳过外发**，卡片带 `warning: secret_like_semantic_skipped`。
- **Δ2（建议立即）**：失败原因可读化——把 `SECRET_REJECTED` 死信的 `error_summary` 从
  "job execution rejected or failed" 改为可解释文案，并让 health 通知按原因分组。
- **Δ3（可选）**：给 `rebuild_index` 一个运维入口（CLI 子命令或定期作业），并实测一次全量重建。
- **Δ4（可选，V2 级）**：替代型变更识别（"我改主意了"）→ 生成"降级建议"进 Inbox（保持 D4 保守）。
- **Δ5（可选，V2 级）**：项目依赖连线图（新表 + 新工具）。

**决策点**：D-A 见 Δ1（拒收 vs 本地降级）；D-B 是否现在补 Δ2/Δ3（小改动）。

## 九、Zafiro 实测缺陷 D1–D8 的对账与修复台账（2026-09-25 补记）

用户的安卓端（Zafiro，MCP over HTTPS）实测暴露了 8 条缺陷。逐条对账：**3 条服务端根因**（D1/D2/D3 的服务端侧），
**5 条属客户端**（D4–D8，无源码，只写建议）。分类依据是"谁的代码决定这条链能不能通"，不是"谁先被用户看见"。

### 9.1 分类与处置

| 缺陷 | 归属 | 根因（服务端真相） | 处置 | 验证证据 |
|---|---|---|---|---|
| D1 治理工具 SCOPE_DENIED | 服务端 | `create_deletion_plan`/`create_review_item` 按**数据 scope** 授权（`review.write` + `knowledge`），而默认档只在 `review` scope 发 grant → 在门禁之前就被拒 | 新增运维开关 `review-access --scope <数据域> --access read/write/none`（双确认 + 审计 + 可撤销）；门禁语义改为"返回待确认计划"（见 9.2 第 2 条） | prod：zafiro 授权后 `create_deletion_plan(knowledge)` 返回待确认计划 + `review_item_id`；未授权的 `finance` 仍 SCOPE_DENIED |
| D2 claim 重复冗余 | 服务端 | 抽取管道只 append 不比对：完全相同/近义的候选逐条落库 | 规则化去重三件套：抽取时合并（证据并入已有 claim）+ 每日 `dedupe_claims` 清道夫（完全相同/词元 Jaccard≥0.75 合并、向量余弦≥0.85 与 Jaccard∈[0.5,0.75) 生成 merge_candidate）+ 批准即执行合并；`get_self_context` 只陈述活卡片 | prod：真实数据 34 条扫出 1 组、合并 2 条（用户报的那条"收拢到自有服务器"重复）、1 条疑似近义进 Inbox；卡片 94/94 守恒 |

### 9.2 本次一并修掉的三个"链路死锁"（对账时新发现）

1. **确认工具没暴露**：FR-099 工具面里只有 `create_review_item`/`create_deletion_plan`/`get_deletion_plan`，
   没有 `list_review_items`/`resolve_review_item` → 客户端能"发起"却不能"看"和"批"。D1 的治理链与 D2 的合并链
   在客户端都断在第二环。**用户已确认**：工具面 30 → 32。
2. **高风险门禁的行为链死锁**：`create_deletion_plan` 与 `resolve_review_item` 都以
   `risk=high_risk_deletion` 调 `authorize()`，而策略层对高风险一律抛 `CONFIRMATION_REQUIRED` —
   "要确认才能确认"，两条链都不可能闭合（001 实例的行为链死锁）。
   修法：门禁**回到证据所在处**——提案（建计划）为普通风险、返回"待确认 + 计划详情"；
   执行（批阅）由 store 消费**版本绑定 + 15 分钟过期 + 单次使用 + owner 绑定**的确认项来把关
   （比一个布尔值更强）。策略层的 `_CONFIRMATION_RISKS` 保留给未来"无确认凭据的即时破坏性工具"。
3. **画像视图暴露全部状态**：`get_self_context` 原先不筛 `lifecycle_state`，被合并/过期的历史行仍被当作
   "现在的主张"并列陈述 → 去重之后仍噪声。改为只返回 `candidate`/`active`。

另修一条**测试基建**缺陷：`e2e_postgres_harness` 用 `SET search_path` 挂隔离 schema，
而 `SET` 是事务性的、连接回收（reset-on-return）时会被回滚 → 同一连接上的第二次 reflection 看到空库
（表现为"第二个 AuthoritativeStore 缺表"）。改为连接选项 `options=-c search_path=...`。

### 9.3 客户端建议（D3–D8，交安卓侧）

1. **D3**：会话模型加"分叉关系"（`parent_conversation_id` + `branch_index`）或**稳定会话根 id**，
   归档按根 id 去重；能算 sha256 时给 `save_note` 带 `content_hash`（服务端会复核）。
2. **D4**：分叉命名用"标题 (分支 N)"；`title_edited=1` 时不得自动改写。
