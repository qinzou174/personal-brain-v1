## 一句话白话结论

这份需求要把"你每天随口讲的经历"变成"一年后随口一问就能查到的记忆"——目前靠的是一套零开发的笔记约定，已经能用；本次需求化把它从"口头约定"升格成"有边界、有验收标准的正式需求"，并暴露了 8 个原来没人定义的坑（漏记怎么办、跨年怎么查、隐私怎么算等），其中 3 个值得升级为产品功能。

## 二、反思：8 个原始需求未定义的缺口（含白话与举例）

### G1 年份歧义与跨年合并查询 【建议产品化】
- **白话**：需求说"一年后能查"，但没说两年后怎么办。"历史上的今天"到底只查去年，还是把历史上所有年份的同一天都翻出来？
- **举例**：2027-09-25 问"历史上的今天"，正确答案应该把 2025、2026 两年的 9 月 25 日都给出来；但现在的口令"去年今天"只算一年，搜 `2026-09-25` 只回一年。约定层没定义"把 MM-DD 相同的所有年份合并返回"。
- **涉及**：Zafiro 系统提示词检索口令；若产品化则涉及 search_brain 查询组装层。
- **验证**：写入两个不同年份的假想日后，跨年查询必须同时命中（当前无此用例）。

### G2 漏记日与"无记录日"的应答语义 【约定可解，需写死】
- **白话**：哪天忘了讲，那天就永远是空白。需求没定义"查了但那天没记"该怎么答。
- **举例**：2027-09-25 问历史，但 2026-12-01 忘了记——助手必须答"那天没有记录"，而不是拿别的日期内容编。这是知识库 NOT_FOUND 诚实语义在约定层的映射，必须写进 SKILL.md。
- **验证**：查一个保证无记录的历史日期，应答必须是"无记录"且不混入相邻日期内容。

### G3 补记路径 【约定可解，需写死】
- **白话**：过两天想起"上周五我还去做了 X"，要能补录到上周五的条目里，而不是记成今天的事。
- **举例**：用户说"帮我把 2026-09-20 的事补上"→ 助手必须新写一条`【日常·2026-09-20】`（追加式），而不是改今天、更不能改日期。与 content_hash 折叠机制兼容：同内容折叠、不同内容并存多条（repo 已有归档去重语义，见 project memory #24）。
- **验证**：补记后按 2026-09-20 检索必须命中补记条目，且当天原条目不变。

### G4 时区归属 【约定可解，需写死】
- **白话**："今天"是按谁的时间算？用户在东八区，服务器在别处，跨午夜前后讲"今天"可能差一天。
- **举例**：2026-09-25 23:59 讲的事，若按 UTC 算就成了 09-25 与 09-26 的分界事故。约定必须写死：日期一律按用户本地时区（Asia/Shanghai）由助手侧计算，正文日期是唯一事实。
- **验证**：跨午夜场景写一条，检索日期与用户体感日期一致。

### G5 行动项分流（叙事 vs 待办） 【建议产品化/约定强化】
- **白话**：日常笔记里写"带小猫看病"是行动项，光躺在叙事笔记里不会进待办系统，两头会漂移。
- **举例**：首条实测里"带小猫去看病、银行取钱"既是【日常】叙事又天然是待办；若只记在【日常】里，问"我今天还有什么没办"走 add_todo/list_todos 就查不到。**机制笔记证实**：读路径已联动（按日期检索【日常】后 list_todos 补状态）、待办完成后会顺手记入——但**写入侧分流仍未定义**：用户口述新行动项时，是否自动 add_todo？
- **涉及**：Zafiro SKILL.md §15 写入时机；系统提示词第 4 条已提"查待办"联动但未定义写入侧分流。
- **验证**：讲一段含新行动项的经历后，list_todos 出现对应待办、且按日期检索日常与待办两头都有。

### G6 敏感度口径 【约定可解，需写死】
- **白话**：日常经历含看病、取钱这类个人敏感事，存取时的隐私等级需求里没定。
- **举例**：检索时 `sensitivity_ceiling` 若配低了，敏感日常会被隐私闸门拦住查不到；若无限放开又违反最小暴露。定义：日常记录 sensitivity=personal（或按内容升级 private），检索口令固定 ceiling。
- **验证**：敏感条目以约定 ceiling 可查回，且 finance 域金额不走语义检索（走精确 SQL，repo 既有规则）。

### G7 查询组装规范（防路由偏航） 【约定可解，已部分覆盖】
- **白话**："历史上的今天"这五个字本身搜不出东西，必须先换算成日期字符串再搜——这是约定成败的关键，但只写在助手侧流程里，没写成硬规则。
- **举例**：若助手偷懒直接拿"历史上的今天"当 query，混合检索的语义路径会召回一堆无关"历史"主题内容（repo router 规则：检索路由对宽泛词保守处理）。需求化写死：查询必须以 `YYYY-MM-DD` 字面量为主体，禁止裸自然语言日期词。
- **验证**：与 repo 既有 `tests/unit/test_router_accuracy.py` 矩阵一致；新增跨年字面量用例。

### G8 漏记提醒缺失 【建议产品化】
- **白话**：现在全靠用户主动讲，忘了就断档，系统不会提醒。一年后翻历史会发现一堆空洞。
- **举例**：就像冰箱塞满才想起大扫除——等发现断档已经补不回来了。产品化方向：每日 03:10 摘要作业链（repo 已有定时作业框架，见 project memory #19）加一条"今日【日常】未写入 → Inbox 提醒"，复用主动通知机制（#20，60 分钟冷却）。约定层无解，这是最值得做的一条。
- **验证**：模拟当日未写入，次日作业产生一条提醒且不重复轰炸。

## 三、需求规格（正式化）

### 功能需求

- **FR-1 每日记录（追加式）**：用户讲当天经历时，AI 当场写入/追加 `【日常·YYYY-MM-DD】` 笔记；日期必须出现在正文；一天允许多条，语义为"追加"而非"覆盖"。
  - AC（Given-When-Then）：Given 用户在 2026-09-25 讲"下午去了银行" When AI 记录 Then 产生或追加一条含 `【日常·2026-09-25】` 的笔记，且原有条目不被修改或删除。
- **FR-2 按日检索**：查询以日期字面量为主体；命中该日期全部条目（含多条追加）；无记录时诚实应答"那天没有记录"（G2）。
  - AC：Given 库内 2026-09-25 有 2 条 When 问"2026-09-25 做了什么" Then 两条都返回；Given 2026-01-01 无记录 When 查询 Then 应答无记录且不混入其他日期。
- **FR-3 口令触发**：识别"历史上的今天 / 去年今天 / 昨天我做了什么"，先换算日期再检索（G7）；跨年语义按 G1 拍板结果执行。
- **FR-4 补记**：按用户指定的历史日期写入对应 `【日常·YYYY-MM-DD】`，不改动今日条目（G3）。
- **FR-5 行动项分流**：经历中的可执行事项同步结构化待办（add_todo），日常笔记保持叙事（G5）。
- **FR-6 敏感度**：日常记录与检索的 sensitivity 口径按 G6 拍板值固定。

### 非功能需求

- **NFR-1**：日期检索延迟不劣于现有混合检索基线（er12 benchmark 报告为对照）。
- **NFR-2**：写入链路遵守 ER-07（幂等/断网容忍）：save_note 幂等键必传，重复口述不产生重复条目（content_hash 折叠）。

### 明确不做（本阶段）

- 不新建 daily_logs 表、不做晨报自动推送（备选 A，未来产品化再议）。
- 不回填历史会话归档为【日常】条目（备选 B：历史归档无结构化日期，误填风险高）。
- 不动 Personal Brain V1 服务端代码——现有能力已满足 FR-1..6 的存储与检索。

## 四、备选方案

- **备选 A 产品功能化**（新建表 + 定时提醒 + 专用查询工具）：可见效果更好（自动提醒、结构化查询），但成本高；本任务判为"约定层已覆盖核心，仅 G1/G5/G8 值得未来产品化"。
- **备选 B 历史回填**：可见效果是"第一天就有历史可查"，但归档数据无可靠日期结构，误填会污染记忆——拒绝。
