# Feature Specification: 笔记更正/删除与 AI 消费体验完善

**Feature Branch**: `[003-correction-delete-ux]`

**Created**: 2026-09-25

**Status**: Draft

**Input**: User description: "个人知识库 AI 消费体验完善：笔记更正/待办删除/账目更正/时间范围检索/索引提示/实时冲突提示/路由词表/同名提示/A类语义/已裁决语义/项目删除自授权，共 11 项（SIMTEST 2026-09-25 发现 O-01~O-08、N-01~N-04、项目删除权限缺口）"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 笔记写错了能改（取代语义）(Priority: P1)

用户口述了一条笔记，事后发现内容错了。用户（或 AI 助手）发起"更正"：系统写入更正后的新笔记，同时把旧笔记从检索视野中移除（保留在归档历史中可追溯），此后检索不再把旧错误内容当作有效答案返回。

**Why this priority**: 用户明确要求"一定要解决"。错误信息留在检索视野里会被 AI 当真话引用，是知识库可信度的最大威胁。

**Independent Test**: 写入错误笔记 → 发起更正 → 检索旧关键词不再命中旧内容、检索新内容命中更正版 → 通过。

**Acceptance Scenarios**:

1. **Given** 库中存在一条激活状态的旧笔记，**When** 用户发起更正（提供旧条目标识与新内容），**Then** 系统产生一条新笔记，旧笔记退出检索视野（检索不再命中），但旧笔记原文在归档中保留可追溯
2. **Given** 更正已发生，**When** 用户检索新内容的关键词，**Then** 只有更正版命中
3. **Given** 用户试图更正一个不存在或已删除的条目，**When** 发起更正，**Then** 系统返回诚实的"不存在"错误而非静默成功
4. **Given** 更正动作完成，**Then** 响应中同时给出新条目标识与被取代的旧条目标识（审计与追溯）

### User Story 2 - 记错的待办能删（Priority: P1)

用户建了一条待办后发现是误建。用户删除该待办：它从待办列表与统计中消失，不再永远留在"已完成"里充当噪音。删除是低风险操作，不需要治理确认门禁，但保留审计记录。

**Why this priority**: 用户明确"要解决"。误建待办永久留存会污染待办统计与回顾体验。

**Independent Test**: 建一条待办 → 删除它 → 待办列表不再显示、统计不含它 → 通过。

**Acceptance Scenarios**:

1. **Given** 存在一条待办，**When** 用户删除它，**Then** 待办列表不再返回该条目
2. **Given** 待办已被删除，**When** 再次删除或以旧版本号操作，**Then** 返回诚实错误（不存在/版本冲突）
3. **Given** 删除动作发生，**Then** 审计记录包含操作者、目标与时间

### User Story 3 - 记错的账能改（Priority: P1)

用户记了一笔账发现金额错了。用户对该账目发起"更正"：旧账退出有效集合，新账（正确金额）生效，汇总金额立即反映更正结果。旧账在历史中保留（符合账目"只追加、可追溯"的合规传统）。

**Why this priority**: 金钱数据的准确性是硬需求（ER-04）。汇总错误会直接误导用户。

**Independent Test**: 记一笔 99 元的账 → 更正为 9.9 元 → 汇总只算 9.9，旧 99 不再计入 → 通过。

**Acceptance Scenarios**:

1. **Given** 存在一笔激活的账目，**When** 用户更正其金额，**Then** 旧账退出有效集合，新账生效，汇总按新账计算
2. **Given** 更正请求带非法金额（0/负数/超精度/非数字），**When** 提交，**Then** 返回明确的校验失败错误（不静默、不崩溃）
3. **Given** 更正完成，**Then** 新账与被更正的旧账之间的关联可追溯（响应含双方标识）

### User Story 4 - 写入后知道"什么时候能搜到"（Priority: P2）

用户写入一条内容后立即搜索，系统在写入响应中明确告知该内容"已入索引队列，稍后可检索"，避免用户误以为写入失败。

**Why this priority**: 消除"刚写完就搜不到"的困惑，成本极低。

**Independent Test**: 写入任一条目 → 响应中包含索引状态提示 → 通过。

**Acceptance Scenarios**:

1. **Given** 任意会产生检索卡的写入操作，**When** 写入成功，**Then** 响应包含索引状态为"排队中"的提示字段

### User Story 5 - 按时间范围回看（Priority: P2）

用户问"上周记了什么""9 月 1 日到 15 日去了哪"。AI 可以按内容发生时间过滤检索结果，只返回该时间段内记录的条目。

**Why this priority**: 时间是个人记忆最自然的检索维度，缺失它使"回顾"类问题只能靠语义猜测。

**Independent Test**: 写入两条不同时间标记的笔记 → 按时间范围检索 → 只返回范围内的条目 → 通过。

**Acceptance Scenarios**:

1. **Given** 库中有不同时间记录的条目，**When** 用户按时间范围检索，**Then** 只返回记录时间落在范围内的条目
2. **Given** 一条无法判定记录时间的条目，**When** 用户按时间范围检索，**Then** 该条目被诚实排除（不出现在结果中冒充命中）

### User Story 6 - 立 contradictory 主张时当场提醒（Priority: P2）

用户提出一条与已有主张意义相反的新主张时，系统在响应中当场提示检测到的矛盾（而不是等到次日凌晨的批量扫描），由用户自行决定保留或撤回。

**Why this priority**: 矛盾主张当场可见可以避免用户在不知情下积累自相矛盾的画像。

**Independent Test**: 先立主张 A，再立与 A 相反的主张 B → B 的响应包含矛盾提示 → 通过。

**Acceptance Scenarios**:

1. **Given** 库中存在某主题的激活主张，**When** 用户提出同主题相反极性的新主张，**Then** 新主张的响应包含矛盾提示（指向已有主张）
2. **Given** 新主张与已有主张无极性冲突，**When** 提交，**Then** 响应不含矛盾提示

### User Story 7 - 项目创建者能删除自己的项目（Priority: P2）

创建了项目的用户，对该项目发起治理删除时不再被权限拒绝：创建项目时的自动授权补齐删除所需的审核权限。

**Why this priority**: SIMTEST 实测发现创建者永远无法删除自己的项目，只能靠运维手工授权——治理闭环的最后一个断点。

**Independent Test**: 新建项目 → 以创建者身份对该项目发起删除计划 → 不再 SCOPE_DENIED → 通过。

**Acceptance Scenarios**:

1. **Given** 用户刚创建了一个项目，**When** 对该项目发起删除计划，**Then** 权限检查通过（不再 SCOPE_DENIED）
2. **Given** 非创建者的其他客户端，**When** 对该项目发起删除计划，**Then** 仍然 SCOPE_DENIED（不放宽他人权限）

### User Story 8 - 自然说法也能路由到精确查询（Priority: P3）

用户用日常口语问"有什么要做的事""最近买了什么"，系统路由到结构化精确查询（待办列表/账目汇总），而不是掉进语义搜索碰运气。

**Why this priority**: 提升结构化数据的命中率，属于既有路由能力的词表补充，成本低。

**Independent Test**: 一组自然说法矩阵逐条检查路由结果 → 通过。

**Acceptance Scenarios**:

1. **Given** 一组覆盖常见口语的测试矩阵，**When** 逐条发起检索，**Then** 待办/账目意图的自然说法命中精确路由

### User Story 9 - 建同名项目时有提示（Priority: P3）

用户创建与既有存活项目同名的项目时，创建成功但响应中提示已存在同名项目，避免无意间重复立项。

**Why this priority**: 数据隔离已验证无碍，提示属于低成本防呆。

**Independent Test**: 已有项目 X 的情况下再建同名项目 → 创建成功且响应含同名提示 → 通过。

**Acceptance Scenarios**:

1. **Given** 存在存活项目「旅行」，**When** 再建同名「旅行」项目，**Then** 创建成功且响应包含同名提示（含既有项目标识）

### User Story 10 - A 类主张的语义与状态一致（Priority: P3）

用户以 A 类（"记下就生效"）提交的主张，入库即为生效状态；B 类保持候选语义。状态展示与口令语义一致，AI 不再误读。

**Why this priority**: 语义与实现不一致会让 AI 对用户画像的可靠性产生错误判断。

**Independent Test**: 分别提交 A/B/C 三类主张 → 检查各自生命周期状态 → A 为生效、B/C 为候选/待确认 → 通过。

**Acceptance Scenarios**:

1. **Given** 用户以 A 类提交主张，**When** 查询画像，**Then** 该主张为生效状态
2. **Given** 用户以 B/C 类提交主张，**When** 查询画像，**Then** 状态分别为候选/待确认（行为不变）

### User Story 11 - 已裁决的事项有明确的"已裁决"反馈（Priority: P3）

对已经裁决过的审核项再次发起裁决时，系统返回明确的"该项已裁决"反馈（含当前状态），而不是误导性的"需要确认"。

**Why this priority**: 消除客户端的状态歧义；属低成本语义修正。

**Independent Test**: 裁决一个审核项 → 再次对同一项发起裁决 → 返回"已裁决"反馈 → 通过。

**Acceptance Scenarios**:

1. **Given** 某审核项已完成裁决，**When** 再次发起裁决，**Then** 返回明确的"已裁决"反馈（而非"需要确认"）

### Edge Cases

- 更正笔记时，旧条目已被删除：返回诚实的"不存在"
- 更正笔记时，新内容与旧内容完全相同：仍执行（内容哈希折叠不适用——用户明确要求更新），响应如实反映
- 删除待办时使用过期版本号：返回版本冲突
- 更正账目时新金额非法：返回校验失败，旧账不受影响
- 时间范围检索时范围起止颠倒（from > to）：返回空结果或校验失败（记录契约）
- 实时冲突提示只提示、不阻止：用户坚持保留矛盾主张的权利不受影响
- 同名提示不阻止创建：项目数据隔离已验证，提示仅防呆
- 新工具全部走既有授权映射（对应域的 read/write 权限），不产生新的授权面

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统必须提供笔记更正能力：以旧条目标识与新内容发起更正，产生新条目并将旧条目从检索视野移除（归档保留）
- **FR-002**: 系统必须提供待办删除能力：删除后的待办不再出现在列表与统计中
- **FR-003**: 系统必须提供账目更正能力：更正后旧账退出有效集合、新账生效，汇总立即反映
- **FR-004**: 所有产生检索卡的写入操作，响应必须包含索引状态提示
- **FR-005**: 检索必须支持按内容记录时间过滤（起止范围）
- **FR-006**: 画像主张提交时，若检测到与既有主张的极性冲突，响应必须包含矛盾提示（不阻止提交）
- **FR-007**: 意图路由必须覆盖常见自然说法的待办/账目意图
- **FR-008**: 创建同名项目时，响应必须包含同名提示（不阻止创建）
- **FR-009**: A 类主张入库必须为生效状态；B/C 类行为保持不变
- **FR-010**: 对已裁决审核项的重复裁决，必须返回明确的"已裁决"反馈
- **FR-011**: 项目创建者的自动授权必须包含对该项目的治理删除权限
- **FR-012**: 以上全部新能力必须走既有授权模型（对应域权限），不产生新的授权面；所有变更保留审计记录

### Key Entities *(include if feature involves data)*

- **笔记（raw intake）**：带生命周期状态（激活/已删除/被取代语义通过归档表达）；更正动作产生新条目并归档旧条目
- **待办（todo）**：带生命周期状态；删除为终态迁移
- **账目（expense）**：带版本与种类；更正产生新版本条目并归档旧条目，汇总只计有效条目
- **画像主张（self claim）**：带类别、政策类（A/B/C）、生命周期状态与确认标记
- **审核项（review item）**：带状态（待裁决/已批准/已拒绝）与期望版本
- **检索卡（search index entry）**：带内容时间元数据以支持时间范围过滤；被删除/被取代目标的检索卡必须同步移除

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 更正一条笔记后，检索旧内容关键词命中数为 0，检索新内容命中更正版（可演示）
- **SC-002**: 删除一条待办后，列表与统计中该条目消失（可演示）
- **SC-003**: 更正一笔账后，汇总金额立即等于更正后的期望值（可演示）
- **SC-004**: 100% 的产生检索卡的写入响应包含索引状态提示
- **SC-005**: 时间范围检索只返回范围内的条目（边界含/不含语义有明确契约）
- **SC-006**: 相反极性主张提交的响应矛盾提示率 100%（同主题已有时）
- **SC-007**: 自然说法路由矩阵全部命中预期通道
- **SC-008**: 项目创建者对自建项目的删除计划不再出现权限拒绝
- **SC-009**: 全量回归测试零失败；既有客户端无需任何配置变更

## Assumptions

- 更正/删除语义沿用既有"归档保留 + 检索移除"的生命周期模型（宪法原则 V：矛盾/被取代信息保留为历史）
- 待办删除为低风险操作，不走治理确认门禁（与"完成"同级）；项目删除仍走完整治理门禁
- 时间范围过滤以"内容记录时间"为准（用户口述内容的原始时间戳），时区沿用 Asia/Shanghai 语境下的既有约定
- 新工具授权复用对应域的既有权限（笔记更正→knowledge.write、待办删除→todo.write、账目更正→finance.write、时间检索→search.read），不新增权限种类
- 实时冲突提示为尽力而为的轻量比对（同类别+极性相反），深度冲突分析仍由每日批处理负责
- 既有客户端无需任何配置变更即可使用新能力；新工具对新客户端自动可用
