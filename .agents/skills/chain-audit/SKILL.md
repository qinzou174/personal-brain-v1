# Chain-Audit（拉绳审查 · 侦探式链路追踪）

审查本项目的组织方式是**链路追踪**，不是类别清单：先找所有"消息进入的管线"（绳子头），从入口顺运行时序一路向下挖，每挖到一个环节当场审"上游 / 逻辑 / 下游消费"三件事，发现下游就继续挖、发现分支就记录并深入，直到一根绳子从头到尾走完。类别检查点只是拉绳过程中随时抽查的工具。

## 0. 铁律

- **跟着绳子走，不按类别翻堆**。禁止"先查死表、再查词表、再查并发"这种切碎绳子的组织方式；一切发现都挂在"哪根绳子、哪个环节"上。
- **每根绳子拉到底**。不允许停在"主干通了"就收工；分支、死胡同、断点都要走到。
- **侦探式推进**：收集 → 反思（哪像断了/哪像说谎）→ 再深入。禁止一次横扫后一次性汇总。
- **白话交付（强制）**：每个环节、每条发现必须配「白话」+「举例」+「证据文件:行号」+「严重度」+「断点位置」。

## 0.5 底层逻辑化：一法通全链（本 skill 的灵魂）

- **全项目只有一种方法：链路追踪。** 没有"情绪系统审查""记忆系统审查""反思审查"这类分系统的段落——它们全部是**同一条闭环链路上的节点**，顺着链路走就会自然经过并审查到每一个。
- **闭环保证覆盖**：从入口进入，沿运行时序经过 消息 → 储存 → 情绪 → 记忆变化 → 反思 → 元认知 → 欲望 → 涌现 → 表达 → 世界对接 → B 端事件回流 → 回到情绪/记忆，最终构成一张闭环图。**审完闭环 = 全系统覆盖**，不需要也不会单独开审任何系统。
- 所有环节适用**同一套底层方法**（每环三问 + 检查点抽查 + 侦探式推进），不因环节/系统而变。检查点只是拉绳过程中的随身工具，不是分系统的工作表。

## 0.6 系统识别：先建全景地图，再走链（防止漏系统）

**本 skill 的入口绳子只是"路径"；系统全景才是"全覆盖的标尺"。** 先自上而下盘点项目全部系统，再走链路，最后用地图核对——任何系统未被链路经过 = 审查缺口，必须补查。

1. **建系统全景清单**（参考 `references/systems-map.md`）：A 端（消息/缓冲/提示词/LLM/工具/欲望/任务/情绪/身体/安全/记忆/反思认知/人格/关系/媒体/快照/调度/账本/承诺/主动消息）+ B 端（世界状态/场景推理/事件/经济/旅程/社交/实体登记）+ C 端（天气/B站/表情/追踪）。
2. **每系统标三件事**：职责一句话、关键文件、它的"生产→存储→消费"落在哪条链上。
3. **走链时对照地图打勾**：每经过一个系统就打勾；走完全部绳子后，**未打勾的系统 = 审查缺口**，单独补走它的链路（从它的生产者入口进，走到消费者尽头）。
4. 系统清单本身也是审查对象：清单里缺一个系统 = 地图不完整 = 项目里可能存在没人审的角落。

## 1. 入口盘点（找绳子头）

先枚举本项目的全部"消息/生活进入管线"，一根不落：

- A 端消息管线：telegram（telegram_bot/telegram_channel）、apk（pipeline.py → run_ai_turn）、http（/v1/chat/completions → queue worker）——都汇入 `session.chat`
- A 端后台生活循环：tick 心跳（shared_runtime 300/900s）→ TickStageRunner 十一阶段
- B 端流入：事件总账（world_client.poll_events / SSE）→ `_process_world_event_batch` → 主观化 → 记忆
- 定时/触发：反思（墙钟门）、认知、欲望生成（CDG/欲望板）、行为上报

产出：入口清单（每根绳子的名字、入口文件:行号、白话一句话）。

## 2. 对每根绳子：按运行顺序 DFS 向下挖（全链闭环主轴）

以"运行时序"为主轴，从入口一路追到尽头再回流闭环。**以下是闭环主轴（不是分系统清单）——顺着它走，消息/储存/情绪/记忆/反思/元认知/欲望/涌现/表达/世界对接全部自然经过**：

```
消息进入 → 缓冲 → 意图/平凡判定 → 提示词工程（material 收集）
→ 提示词组装（orchestrator）→ LLM 调用（chat_stage1/tool 链）
→ 输出解析（双产出/情绪自报）→ 状态应用（情绪/身体/安全感）
→ 记忆写入（accumulator/gate/SQLite/向量）→ 记忆消费（检索/压缩/反哺）
→ 反思 / 元认知 → 欲望生成与裁量 → 涌现 / 自主行为 → 表达（浮上表层）
→ 世界对接（位置/行为/事件上报）→ B 端事件回流 → 回到情绪/记忆（闭环）
```

走到某环节时，**每个下游继续深入、每个分支记录后逐个追**——情绪系统会自然引出数值逻辑→商品；记忆系统会自然引出动态注入→索引→压缩。不停在表面，直到闭环。

## 3. 每环三问（当场审）

挖到任何一个环节（函数/字段/表/LLM 调用/prompt 块），当场问：

1. **上游对不对**：输入从哪来？来源可靠吗（生产者明确/事实分层/来源标记）？
2. **逻辑对不对**：这个环节处理正确吗（字段读对了吗/类型/单位/版本/边界/失败路径）？
3. **下游能消费吗**：输出到哪？有没有消费者？消费者读的字段一致吗？最终体现在哪（用户可感知/行为差异）？

同时顺带抽查**检查点清单**（见 references/checklist.md）：词表替判、表达覆盖事实、替 AI 决定、死字段/死表、配置漂移、并发超时、孤儿任务、硬编码身份、活动硬解码、推断冒充事实等。**检查点是抽查，不是组织方式。**

## 4. 分支与递归推进

- 环节产出的**每个下游**都继续深入（情绪系统 → 数值逻辑 → 商品效果；记忆系统 → 动态注入 → 索引）。
- 遇到**分支**（一个产出多个消费者 / 一个环节多个来源）记录为分支点，逐个追到底。
- 遇到**死胡同**（有产无消 / 有写无读 / 引用了不存在的东西）——**这就是断点 bug**，记录后继续下一分支。
- 挖到字段/表/LLM 调用级别：查引用完整性、上下游是否一致、逻辑正确性。

## 5. 收集 → 反思 → 再推进

- 每挖一段，反思：哪里像断了？哪里"能跑但可疑"？哪里该有消费却找不到？
- 可疑点立即反向搜索验证（从字段/表/trigger/日志往回找读它的人）。
- 不停在"第一个根因"：同一条绳子上可能有多个断点，都记。

## 6. 产出

按每根绳子汇报：

- **链路图**：绳子从头到尾的环节序列（文件:行号 + 白话一句话每个环节）
- **断点清单**：每个断点 = 「白话」+「举例」+「证据」+「严重度」+「断在哪一环」
- **分支账**：记录过的分支及其去向
- **覆盖状态**：哪些绳子走完、哪些没走完（明确标 PARTIAL 并说明剩余）

## 7. 与其它 skill 的关系

- `full-project-audit`：本 skill 是其"生产者→消费者"Pass 的深化与运行时序化。全量多域审计用它起头，链路深挖用本 skill。
- `project-analysis`：单点诊断用；本 skill 是"从头到尾整根拉"。
- `engineering-tooling`：重复机械检查（vulture 死代码、链路上每个环节的引用核对）工具化后并入本 skill 的 scripts/。
- `system-causal-audit`：以"一个现象 / 一条链 / 一个改动的影响"为起点的**因果深度**审查——向上根因 + 向下影响 + LLM 真实输入输出 + 时间契约（Temporal Contract），并做"局部正确、全局错误"的整链判定。本 skill 负责**覆盖广度**（全项目拉网、33 系统地图打勾）；需要"这条链为什么这样、改这里会动谁"时转它。它反向引用本 skill 的 `references/systems-map.md` 作为系统清单，不另建地图（防两套地图漂移）。

## 8. 约束

- 只读审查；修复需用户另行授权。
- 词表/哲学类发现：修复前必须走 design-intent-alignment 确认正确行为（判定归 LLM/自报协议），不直接建议删。
- 证据必须文件:行号；白话/举例是解释层，不替代证据层。
